How zsh resolves a command

…and the trick that lets asm hijack claude --resume and codex resume without you noticing.

1. What a shell actually does

zsh (or bash, or fish) is a REPL for the operating system. You type a line, it reads, parses, decides what that line means, runs something, and prints the output. The "decides what that line means" step is where all the interesting stuff lives.

When you type: 

claude --resume abc123

zsh has to answer: what is claude? It's not a keyword. It's a name. zsh walks through a fixed lookup order to figure out what the name refers to.

2. The name resolution order

This is the whole secret. zsh checks these places, in this order, and stops at the first hit:

1. alias
Simple text substitution defined with alias claude=.... Limited: can't inspect arguments.
2. function
A named block of shell code defined with claude() { ... }. Can look at arguments, branch, call other things. This is where the trick lives.
3. builtin
Commands baked into zsh itself: cd, echo, command, exec. You can't override these by editing PATH.
4. hashed
A cache of "I already looked up the full path to claude last time, it lives at /opt/homebrew/bin/claude." Refresh with rehash.
5. PATH lookup
zsh walks each directory in $PATH from left to right, looking for an executable file named claude. First match wins.
6. ✗ command not found
Nothing matched anywhere. zsh prints the familiar error.

Aliases, functions, and builtins all live inside the running zsh process. Hashed entries and PATH lookups produce a full filesystem path, which zsh will then fork() + execve() as a separate program.

3. How zsh starts: where do functions come from?

When you open a new terminal tab, zsh starts as an interactive login shell. Before showing you the prompt, it sources a chain of config files in a fixed order. The one almost everyone edits is: 

~/.zshrc

Everything in ~/.zshrc runs inside the current shell — definitions stick. If ~/.zshrc contains: 

claude() {
  # intercept --resume; pass everything else through
  for arg in "$@"; do
    [[ "$arg" == "--resume" ]] && exec asm --filter claude
  done
  command claude "$@"
}

then your shell now knows about a function called claude. Resolution order says functions are checked before PATH. The real binary at /opt/homebrew/bin/claude is still there — it just isn't what your typed name resolves to anymore.

4. Before and after, side by side

Same command, two different shells. The only difference is whether the function exists.

Before — no function

You type:

claude --resume abc
  1. no alias
  2. no function
  3. not a builtin
  4. PATH: /opt/homebrew/bin/claude

zsh forks, execs the real Claude CLI with ["--resume", "abc"] as argv. You get Claude's native resume picker.

After — function defined

You type:

claude --resume abc
  1. no alias
  2. function: claude()

zsh runs the function body in the current shell. The loop sees --resume, fires exec asm --filter claude. You get the asm list with @claude pre-applied.

5. Two builtins doing all the work

command — "skip the function lookup"

Inside a function called claude, writing claude "$@" would call the function again — infinite recursion. command claude "$@" tells zsh: "start resolution from step 3 (builtins) onward, skipping aliases and functions." That's how you call the real binary from inside your override.

exec — "replace this process, don't spawn a child"

Normally when a shell runs another program, it does fork() (make a copy of itself) then execve() (replace the copy with the new program). Your shell stays around as the parent, waiting for the child to exit.

exec asm --filter claude skips the fork. The running zsh process is replaced in place by asm. Same PID, same terminal, same controlling tty. When asm exits, the shell session ends — which is exactly what you want for "resume into this session." It feels seamless because there's no parent shell sitting underneath waiting.

Why this matters for the asm case: Codex and Claude Code both take over the terminal (raw mode, alternate screen buffer, etc.). If asm launches them as a child and then waits, you'd briefly see asm render, then a child program render on top, then on exit you'd be back in asm's screen for a frame before zsh redraws. exec means asm hands the terminal off cleanly and doesn't come back.

6. What the process tree looks like

Without exec

zsh (pid 41001) ── the shell sitting at your prompt
└── asm (pid 41089) ── forked from zsh; runs the picker
└── claude (pid 41112) ── forked from asm; runs the agent

When claude exits, you're back in asm. When asm exits, you're back in zsh. Two layers of "where am I" the user has to track.

With exec

zsh (pid 41001) ── replaced in place by asm, which is replaced in place by claude
^ now this PID is claude. No extra processes.

When the agent exits, the shell session is done. Open a new terminal tab for a fresh one. This is what people expect.

7. Putting it all together

The full proposed function for ~/.asm/shell-hooks.zsh

# sourced from ~/.zshrc by `asm install`

claude() {
  for arg in "$@"; do
    if [[ "$arg" == "--resume" ]]; then
      exec asm --filter claude
    fi
  done
  command claude "$@"
}

codex() {
  if [[ "$1" == "resume" ]]; then
    exec asm --filter codex
  fi
  command codex "$@"
}

The one-line bootstrap added to ~/.zshrc

[[ -f ~/.asm/shell-hooks.zsh ]] && source ~/.asm/shell-hooks.zsh

That's it. asm install writes the file and adds the line (idempotently, checks for the line first). asm uninstall reverses both. No magic, no daemon, no PATH games — just two function definitions getting picked up by zsh's normal resolution order.

8. What's different from how rtk does it

rtk is a Claude Code PreToolUse hook. It only fires when the Claude Code agent invokes Bash with a command like git status — the hook rewrites the invocation to rtk git status before it runs. None of this is visible to your shell. You type git status in your own terminal, rtk does nothing.

asm's shell hook is the opposite: it lives in your shell, fires only when you type a command at the prompt, and is completely invisible to Claude Code or Codex when they call git/whatever themselves.

Both are valid; they just operate at different layers. Combining them would be fine — they never see each other.

Gotcha: shell functions only exist in interactive shells. If you launch claude --resume from a script with #!/bin/sh, no function is loaded. That's almost always what you want — scripts should keep using the real binary, not pop a TUI. If you ever did want scripts to be hijacked too, you'd need the PATH-shim approach (a file named claude earlier in $PATH), not the function approach.
